# TransitOptima: Health-Aware Multimodal Trip Planning for Surat with Real-Time Pollution Exposure

**Live demo:** [surat-transit-optimiser-3e9j.vercel.app](https://surat-transit-optimiser-3e9j.vercel.app/)

# Abstract

Urban commuters routinely decide how to travel on the basis of time and money, while the air they breathe along the way, often the real difference between one mode and another, stays invisible. TransitOptima makes that third axis explicit. It is a full-stack, door-to-door trip planner for the city of Surat that compares the **Bus Rapid Transit System (BRTS)**, **shared auto-rickshaws**, and a **private car** on travel time, monetary cost, carbon dioxide emissions, and the **personal PM2.5 dose a traveller actually inhales**. Public-transit journeys are solved with **A\*** search over a station graph; for open-road car and auto journeys the **fastest** route is solved with **A\*** over a layered waypoint graph, while the **balanced** and **cleanest-air** alternatives are generated by a **breadth-first search** over the same graph, all ranked by travel time and air quality. Air quality is drawn through a graded hierarchy of **live Central Pollution Control Board (CPCB) ground sensors**, a **World Air Quality Index (WAQI) station**, and the **Copernicus Atmosphere Monitoring Service (CAMS) model**, with the active source and its uncertainty disclosed at all times. Travel time is traffic-aware through the **TomTom Routing API**, with a calibrated offline model as a fallback. Throughout, the system reports the measured error of each estimate against a live reference where one exists, favouring transparency over the appearance of precision.

# 1. Introduction

Air pollution remains one of the most significant environmental health risks in Indian cities, with **fine particulate matter (PM2.5)** contributing substantially to **respiratory and cardiovascular disease** because of its ability to penetrate deep into the lungs and bloodstream. Conventional trip planners optimise almost exclusively for travel time, occasionally for cost, and never for the pollution a commuter is exposed to in transit, even though that exposure can vary several-fold between an enclosed air-conditioned car and an open three-wheeler on the same road.

TransitOptima addresses this gap for Surat. Given an origin and a destination, it plans a complete door-to-door journey for each available mode, attaches a traffic-aware travel time, a fare or fuel cost, an emissions estimate, and a personal inhaled-PM2.5 dose, and presents the options side by side. The central design principle is **honesty about uncertainty**: every quantity is labelled as measured or modelled, the source of each air-quality reading is stated together with the distance to the nearest sensor, and, where a live ground truth is available, the system displays the actual error of its own estimate rather than a polished but unverifiable number. The result is a decision-support tool that answers a question most planners ignore: which way is not merely fastest or cheapest, but also healthiest.

# 2. Materials and Methods

## 2.1 Study Area and Scope

The study area is the urban region of **Surat, Gujarat**. Trips are planned door to door between two arbitrary coordinates selected on a map or through place search. Three travel modes are modelled: the **BRTS** (a fixed-corridor public bus network), **shared auto-rickshaw pooling**, and a **private car** baseline. The BRTS runs on fixed corridors and is therefore treated as a fixed route; the car and auto travel the open road network and are eligible for route alternatives. All distances are computed on the real street network rather than as straight lines, and all per-mode estimates share the same origin, destination, and traffic conditions so that comparisons are fair.

## 2.2 Data Sources

### *2.2.1 Geocoding and Road Geometry (Nominatim and OSRM)*

Place search and reverse geocoding use the **OpenStreetMap Nominatim** service, biased toward Surat. Road geometry is obtained from the **Open Source Routing Machine (OSRM)**, which snaps a set of waypoints to the driving network and returns turn-by-turn polylines together with route distance and free-flow duration. OSRM is used both to render every route as a real, road-following path and as the geometry generator for the candidate corridors described in Section 2.4.

### *2.2.2 Traffic-Aware Travel Time (TomTom and a Calibrated Offline Model)*

Travel time is resolved server-side so that the routing key is never exposed to the browser. In production a **serverless function** queries the **TomTom Routing API** for a live, traffic-aware estimate; the same logic is available locally through a bundled FastAPI service for development. When a corridor's intermediate waypoints are supplied, TomTom is forced to route through them, so each candidate road route receives its own traffic-aware time rather than the single fastest path.

When TomTom is unavailable, the system falls back to a **calibrated Surat congestion model**. This model shapes the OSRM free-flow time with an hour-by-hour congestion curve, a speed-aware correction derived from the implied free-flow speed, and an additional queueing term for trips that cross the Tapi River, where Surat's north–south flow funnels through a limited number of bridges. A persisted correction factor is updated from each live TomTom observation, so the offline model's future predictions converge toward measured conditions over time.

### *2.2.3 Air-Quality Observations (CPCB, WAQI, and CAMS)*

Air quality is assembled through a three-tier hierarchy, preferring the most trustworthy source available for a given route.

1. **Live CPCB ground sensors** (via the Government of India open-data portal, data.gov.in) are the preferred source. Where two or more in-city monitors are available, the concentration along the route is estimated by **inverse-distance-squared weighting** so that nearby sensors dominate and distant ones act only as a safety net.
2. A **WAQI ground station** is used when one lies within range of the route.
3. The **Copernicus CAMS model** (served through Open-Meteo) is the final fallback, sampled at roughly 500 m intervals along the path.

Surat itself has **no WAQI station** (the nearest is approximately 50 km away in the industrial town of Ankleshwar), which would make a WAQI-only design report the wrong city's air. Because data.gov.in does expose live CPCB sensors inside Surat, the engine prefers and interpolates between those, and the interface always states which source was used and how far the nearest sensor lies.

## 2.3 Public-Transit Journey Planning

BRTS journeys are computed over an explicit **station graph** in which stations are nodes and consecutive stops on a route are edges. The shortest time-path between the entry and exit stations is found with **A\*** search using a **binary min-heap** priority queue and an admissible straight-line-time heuristic, so the search expands far fewer states than an uninformed expansion while still returning the optimal path. Edge cost is modelled from operational parameters rather than a single average speed, combining a dedicated-corridor cruise speed, per-stop dwell time, acceleration and deceleration penalties, an initial headway wait, and a transfer penalty that captures the platform-change time and waiting cost of switching lines. The resulting itinerary is assembled into first-mile walking, riding, transfer, and last-mile walking legs, each snapped to the road network for display.

## 2.4 Exposure-Aware Road Routing

For the car and auto modes, where more than one sensible route usually exists, the open road network is not stored as a graph, so a graph is constructed and searched. A layered set of **candidate waypoint columns** is laid out across the corridor between origin and destination, each column offset perpendicular to the straight line. The **fastest** route is solved with **A\*** over this layered graph, weighting each edge by its real free-flow road time from OSRM and guided by an admissible straight-line-at-top-speed heuristic, so the minimum-time corridor is settled rather than merely picked from a list. For the **balanced** and **cleanest-air** alternatives, a **breadth-first search** enumerates every path that selects one waypoint per column, and each enumerated path is realised as a **real street route through OSRM**, so all candidates follow actual roads and retain genuine distance, traffic-aware time, and measured air quality. Many enumerated paths snap onto the same roads and are de-duplicated, and the number of realised routes is capped to keep the operation responsive on the public routing server.

Each surviving candidate is scored and the set is ranked three ways:

- **Fastest** is the route with the shortest traffic-aware travel time.
- **Cleanest Air** is the route through the **lowest average PM2.5 concentration**, that is, the cleanest air actually breathed, irrespective of time.
- **Balanced** minimises an equally weighted combination of travel time and average PM2.5, each min–max normalised across the candidate set.

A cleaner route is only offered when the detour is worth it. Trips shorter than approximately one kilometre, and cases in which the cleanest route is no more than about 1 µg/m³ cleaner yet at least one kilometre longer than the fastest, collapse all three options onto the single best route, with an explicit note explaining why. When all corridors pass through near-identical air, the interface says so rather than presenting a meaningless difference.

## 2.5 Personal Exposure Model

Ambient air quality is converted into a **personal inhaled dose** for the selected mode. The inhaled mass is the product of the ambient PM2.5 concentration along the route, a **mode microenvironment factor**, a nominal breathing rate, and the trip duration. The microenvironment factors are literature-informed defaults: approximately **0.5** for an enclosed air-conditioned private car, **1.5** for an open auto-rickshaw travelling in the traffic plume, and **0.7** for an air-conditioned bus, with walking legs treated as fully exposed (about **1.2**) and blended by duration for multimodal BRTS trips. All concentrations are classified on the official **United States Environmental Protection Agency (US-EPA)** six-band Air Quality Index scale, with PM2.5 converted to and from µg/m³ using the EPA piecewise-linear breakpoints.

## 2.6 Fare Model

BRTS fares follow the official **Surat Sitilink** progressive distance-slab structure, a deterministic lookup that rises in fixed steps and is capped, with integrated, penalty-free transfers inside the paid zone. A set of **passenger profiles**, including standard, digital-ticket, student, senior-citizen, and prepaid-pass riders, applies the corresponding concession to the computed fare. Profile descriptions, eligibility, and links to the official application channels are presented in the interface so that the discount shown is accompanied by the means to obtain it. Auto-rickshaw cost follows the metered Gujarat tariff split across pooled riders, and the private-car cost and emissions are derived from distance, a user-selectable fuel type (petrol, diesel, or compressed natural gas), and standard per-unit price and emission factors.

## 2.7 Accuracy Characterisation and Error Reporting

Rather than asserting fixed accuracy figures, the system measures and displays its error against a live reference wherever one exists.

- **Travel time.** When TomTom is available, the displayed time is the live TomTom value, which serves as the reference. The interface additionally reports how far the offline calibrated model would have been from that reference, expressed as a signed difference and a percentage, so the reliability of the fallback is transparent. This deviation is treated as acceptable below roughly 10 percent and notable above roughly 25 percent.
- **Distance.** The map distance from OSRM is cross-checked against TomTom's own route distance for the same trip; the two routing engines differ only by their choice of roads and turns, and the difference is reported, flagged as small below roughly 5 percent.
- **Air quality.** Because there is no independent second source to compare against in real time, each PM2.5 and AQI reading carries an **estimated uncertainty** rather than a measured error. The estimate grows with distance from the nearest sensor and with the coarseness of the source: roughly 8 percent plus 1.2 percent per kilometre for CPCB sensors, roughly 12 percent plus 1.5 percent per kilometre for a WAQI station, and a flat 30 percent for the coarse-grid CAMS model. The estimate is clearly labelled as such.

# 3. Results

## 3.1 System Outputs and Mode Comparison

For any origin–destination pair, the system produces a ranked, side-by-side comparison of the three modes on travel time, cost, carbon dioxide, and personal PM2.5 dose, alongside an interactive map showing the selected route on the real street network. Selecting BRTS opens a fare-profile chooser that applies the appropriate concession; selecting the private car opens a fuel chooser that re-bases cost and emissions; and selecting car or auto exposes the Fastest, Cleanest Air, and Balanced road alternatives, redrawing and re-measuring the map as the choice changes. An exposure panel reports both the ambient air on the route and the personal dose for the chosen mode.

## 3.2 Reported Accuracy and Transparency

The system's behaviour with respect to accuracy can be summarised as follows.

- **Travel time**: live and traffic-aware when TomTom is reachable; otherwise a calibrated model whose deviation from live conditions is displayed and which self-corrects from past observations.
- **Distance**: real road geometry from OSRM, cross-checked live against a second routing engine and typically agreeing within a few percent.
- **Fare**: a deterministic match to the published Sitilink distance slabs, with concession rates labelled as modelled and linked to official sources.
- **Air quality**: measured from live in-city CPCB sensors where available, falling back transparently to a regional model, with an estimated per-reading uncertainty always shown.

## 3.3 Honest Limitations

CPCB coverage inside Surat is limited to a small number of stations, so genuine intra-city spatial variation in air quality is modest and the CAMS fallback operates on an approximately 40 km grid. The mode-exposure factors are evidence-informed defaults rather than measurements of Surat's specific vehicle fleet. Government data feeds occasionally rate-limit, in which case the system degrades to the coarser model and states that it has done so. Each of these limitations is surfaced in the interface rather than hidden.

# 4. Conclusions

TransitOptima demonstrates that an everyday trip planner can treat **air-quality exposure as a first-class decision criterion** alongside time and cost, without overstating what it knows. By planning BRTS journeys with A\* over a station graph, solving the fastest real-road car and auto route with A\* and generating the cleanest-air and balanced alternatives through a breadth-first corridor search, drawing air quality from live CPCB sensors with principled fallbacks, and reporting the measured error or estimated uncertainty of every quantity, the system turns a sparse and noisy set of inputs into a clear, honest, door-to-door comparison. The same design generalises naturally to other cities as denser sensor networks and richer routing data become available.

## 5.3 Getting Started

Prerequisites: Node.js 18 or later and npm; optionally Python 3.10 or later for the local backend.

```bash
git clone <your-repo-url>
cd smart-transport-optimizer
npm install
cp .env.example .env       # optional keys; the app runs without them
npm run dev                # http://localhost:5173
```

The application runs without any keys: air quality falls back to the free CAMS model and traffic to the on-device calibrated model. Keys unlock live sensor and traffic data.

## 5.4 Environment Variables

| Variable | Scope | Purpose |
|----------|-------|---------|
| `TOMTOM_API_KEY` | Server (Vercel function / backend) | Enables live TomTom traffic-aware ETAs. Without it, the calibrated model is used. |
| `VITE_WAQI_TOKEN` | Frontend | Optional WAQI token (aqicn.org). If absent, WAQI is skipped. |
| `VITE_DATAGOV_KEY` | Frontend | Optional data.gov.in key for live CPCB stations. A shared sample key is bundled for light use. |
| `VITE_BACKEND_URL` | Frontend | Optional. Points the traffic client at a specific backend; if unset, the same-origin serverless function is used. |

Real keys must never be committed; environment files are gitignored.

## 5.5 Tests and Production Build

```bash
npm run preview            # serve the production build locally
```
